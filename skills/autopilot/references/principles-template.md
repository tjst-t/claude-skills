# DESIGN_PRINCIPLES.md テンプレート

以下のテンプレートを使って `docs/DESIGN_PRINCIPLES.md` を作成する。ユーザーとの対話で各セクションを埋める。

```markdown
# 設計原則

## 判断に迷ったときのルール

{優先順位付きで記述。上にあるほど優先。}

1. {例: シンプルさ > 多機能 — 機能を追加するか迷ったら、追加しない}
2. {例: 既存ライブラリ活用 > 自前実装 — 車輪の再発明をしない}
3. {例: ユーザー体験 > 内部コード品質 — 完璧なコードより動くプロダクト}
4. {例: 明示的 > 暗黙的 — マジックナンバーや暗黙の規約を避ける}
5. {例: 最小権限 > 便利さ — セキュリティを犠牲にしない}

## コーディング規約

{プロジェクト固有のルール}

- {例: エラーは早期リターンで処理する}
- {例: コメントは「なぜ」を書く。「何を」はコードで表現する}
- {例: テストはテーブルドリブンで書く}

## UI/UXの方針

{フロントエンドがある場合}

- {例: アクション後は即座にフィードバックを返す（楽観的更新）}
- {例: エラーメッセージは具体的に。「エラーが発生しました」は禁止}
- {例: カラーパレットは○○を基調とする}

## アーキテクチャの方針

- {例: モノリスで始める。マイクロサービス化は必要が証明されてから}
- {例: データベースマイグレーションは後方互換を保つ}
- {例: APIはRESTful、バージョニングはURLパスで}

## やってはいけないこと

{Claudeが自律判断で絶対にやってはいけないこと}

- {例: 既存のAPIのレスポンス形式を変更しない（後方互換性）}
- {例: 外部サービスへの依存を追加しない（自己完結が原則）}
- {例: .envファイルにシークレットをハードコードしない}
```

## 記入のガイドライン

- **判断に迷ったときのルール** がautopilotの核。ここが充実しているほど、ユーザーの期待に近い判断ができる。全セクションの中で最も重要。
- **やってはいけないこと** は安全弁。これを破る判断は絶対にしない。
- 「判断に迷ったときのルール」は **5〜10項目** に絞る。他のセクション（コーディング規約、UI/UX方針、アーキテクチャ方針）は補助的な位置付けで、判断ルールと矛盾する場合は判断ルールが優先。
- 全セクション合わせて **20項目以内** を目安にする。多すぎると項目同士が矛盾して判断が不安定になる。
- マイルストーンレビューのたびに見直して育てていくもの。

> **Note**: テンプレートは日本語で書かれていますが、プロジェクトの言語に合わせて英語で記入しても構いません。

# Autopilot で新規プロジェクトを始める

## 概要

新規プロジェクトを autopilot で開発するための手順書。仕様が明確な場合と、アイデア段階の場合の2パターンを記載。

どちらのパターンでも、最終的に必要なのは:
- `docs/VISION.md` — なぜ作るか、誰のためか
- `docs/DESIGN_PRINCIPLES.md` — 判断基準
- `CLAUDE.md` — プロジェクトコンテキスト
- `docs/ARCHITECTURE.md` — アーキテクチャ概要
- `docs/ROADMAP.md` — スプリント計画

`/autopilot setup` を実行すると、上記すべてが一括で生成される。

---

## パターン A: 作りたいものの仕様がある場合

既に要件定義書、画面設計、API仕様書などがある場合。最速でコードに落とすルート。

### Step 1: autopilot setup を実行

```
/autopilot setup
```

仕様書がある場合、以下のように伝える:

> 「仕様書はこれです（貼り付け or ファイルパス指定）。これを元にセットアップしてください。」

`autopilot setup` が以下を順番に実行する:
1. **VISION / PRINCIPLES 作成** — 仕様書から「なぜ作るか」「判断基準」を抽出
2. **project-init** — CLAUDE.md, ARCHITECTURE.md, Makefile 生成
3. **sprint roadmap** — VISION + ARCHITECTURE からロードマップを一括生成

**ポイント**:
- 仕様書の内容をそのまま転記するのではなく、「なぜ作るか」「判断基準」に変換してもらう
- 仕様書に書かれていない暗黙の判断基準（技術スタック選定理由、UIの方向性等）を補足する
- 「スコープ外」を明確にする — 仕様書に書かれていない機能は全てスコープ外

### Step 2: ロードマップを確認

生成されたロードマップを確認する:
- ストーリーの粒度は適切か
- 最初のスプリントが「動く最小限」になっているか
- マイルストーンの位置は妥当か

問題があればその場で修正。

### Step 3: Autopilot 開始

```
/autopilot start
```

Claude が自律的にスプリントを連続実行。マイルストーンで停止してデモを見せてくれる。

### Step 4: マイルストーンレビュー

デモを見て:
- 期待通り → 「続行」
- 微調整 → VISION/PRINCIPLES を更新して「続行」
- 方向転換 → ロードマップを修正して「続行」

---

## パターン B: 既に sprint-runner で開発中のプロジェクト

CLAUDE.md, ARCHITECTURE.md, ROADMAP.md が揃っていて、手動スプリントで開発を進めている場合。

### Step 1: autopilot setup を実行

```
/autopilot setup
```

既存プロジェクトを検出し、以下が自動的に行われる:
1. **VISION / PRINCIPLES 作成** — 既存のコード・ROADMAP・ARCHITECTURE を読み取って質問を事前に埋めてくれる。回答を確認・補足するだけでOK。
2. **project-init → スキップ**（既に存在するため）
3. **sprint roadmap → スキップ**（既に存在するため）
4. **整合性チェック** — 新しいVISIONと既存ROADMAPの整合性を確認。スコープ外のストーリーや、VISIONに対応するスプリントが無い場合を指摘。
5. **マイルストーン付与** — ROADMAPに `[MILESTONE]` マーカーが無い場合、適切な位置に提案。

### Step 2: 指摘事項を確認

整合性チェックの結果を確認:
- スコープ外と指摘されたストーリー → 削除するか、VISIONのスコープを広げるか判断
- 不足しているスプリント → 追加するか、今は不要か判断
- マイルストーンの位置 → 承認または調整

### Step 3: Autopilot 開始

```
/autopilot start
```

未完了のスプリントから自律実行を開始。既に `[DONE]` のスプリントはスキップされる。

**ポイント**:
- 現在 `[IN PROGRESS]` のスプリントがある場合、そこから再開される
- 既存コードとの整合性はsprint autoのverifyフェーズで確認される
- 手動で進めたスプリントの判断はdecisions.mdには残らないが、それは問題ない

## パターン C: 仕様がない場合（アイデア段階）

「こういうものが欲しい」程度のぼんやりしたアイデアがある場合。Claude と対話しながら仕様を固めるルート。

### Step 1: アイデアを伝える

まず Claude に自由に伝える:

> 「○○を作りたい。ターゲットは△△で、□□ができるようにしたい。」

この時点では完璧でなくてよい。1〜3文で十分。

### Step 2: autopilot setup を実行

```
/autopilot setup
```

Claude がテンプレートに沿って質問してくる:
- 誰のために？
- 何を解決する？
- 成功の定義は？
- やらないことは？
- 参考にするプロダクトは？

回答後、自動的に project-init と sprint roadmap も実行される。

**ポイント**:
- 「わからない」と答えてOK — Claude が推奨を提案する
- 「スコープ外」は特に重要。最初は広めに除外する方が安全
- 参考プロダクトがあると、UI判断の精度が劇的に上がる

### Step 3: ロードマップを対話的にレビュー

生成されたロードマップを確認する:
- ストーリーの粒度は適切か
- 優先順位は正しいか
- マイルストーンの区切りは妥当か

仕様が曖昧な場合、ここはしっかり時間をかける。ロードマップの質が autopilot の出力品質を決める。

### Step 4: Autopilot 開始

```
/autopilot start
```

### Step 5: マイルストーンレビュー（重要）

仕様が曖昧な状態から始めた場合、最初のマイルストーンレビューが特に重要:
- 「思っていたのと違う」は正常 — VISION/PRINCIPLES を更新する
- 「この機能は要らなかった」→ 残りのスプリントから削除
- 「こっちの方が先に欲しかった」→ 実行順序を変更

最初の1-2マイルストーンで方向が固まれば、あとはスムーズに進む。

## 共通: プロジェクト開始時のチェックリスト

`/autopilot setup` が完了すると、以下がすべて揃っている状態になる:

| # | 項目 | 生成元 |
|---|------|--------|
| 1 | git リポジトリが初期化されている | 事前準備 |
| 2 | `docs/VISION.md` | autopilot setup Phase 1 |
| 3 | `docs/DESIGN_PRINCIPLES.md` | autopilot setup Phase 1 |
| 4 | `CLAUDE.md` | autopilot setup Phase 2 (project-init) |
| 5 | `docs/ARCHITECTURE.md` | autopilot setup Phase 2 (project-init) |
| 6 | `docs/ROADMAP.md` にスプリントが定義されている | autopilot setup Phase 3 (sprint roadmap) |
| 7 | ロードマップに `[MILESTONE]` マーカーがある | sprint roadmap が自動付与 |
| 8 | `.gitignore` に `.claude/worktrees/` が含まれる | project-init |

## Tips

### ロードマップの質を上げるコツ

- **最初のスプリントは小さく**: 1-2ストーリー、動く状態で終わる。大きすぎると失敗リスクが高い。
- **マイルストーンは2-3スプリントごと**: 短すぎると停止が多い、長すぎるとドリフトリスク。
- **受け入れ条件を具体的に**: 「ログインできる」ではなく「メール/パスワードで認証し、JWTトークンを返す。無効な認証情報に対して401を返す。」

### VISION / PRINCIPLES のメンテナンス

- マイルストーンレビューのたびに見直す
- 「このルールがあったから良い判断ができた」→ そのまま維持
- 「このルールのせいで変な判断をした」→ ルールを修正
- 「ルールに書いてないことで迷っていた」→ 新しいルールを追加

### いつ autopilot を止めて手動に戻すか

- ドメイン知識が深く必要な判断が連続する場合
- 外部サービスとの統合で実機確認が必要な場合
- デザインの細部にこだわりがある場合
- パフォーマンスチューニングなど、実測が必要な作業
